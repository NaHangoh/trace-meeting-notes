# 0006. 요청 수 제한은 서버 메모리, 고정 창, getRemoteAddr 기준
- 날짜: 2026-10-08
- 상태: 확정

## 배경
미리보기 API(IP당 분당 60회, SPEC F1)와 작업 생성(IP당 시간당 20회, SPEC S4)에 요청 수 제한이 필요하다. 로그인이 없으므로 IP 단위로 센다. 서버 한 대짜리 개인 프로젝트다.

## 선택지
- 카운트 저장 위치
  - 서버 메모리: 추가 구성 요소가 없다. 대신 재시작하면 카운트가 초기화되고, 서버가 여러 대면 대마다 따로 센다.
  - 외부 저장소(Redis 등): 여러 서버가 같은 카운트를 공유하고 재시작에도 유지된다. 대신 운영할 구성 요소가 하나 늘어난다.
- 창 방식
  - 고정 창(창 길이 단위로 정렬): 구현이 단순하고 시계를 주입해 경계를 정확히 테스트할 수 있다. 대신 창 경계 앞뒤로 최대 2배까지 통과한다.
  - 이동 창·토큰 버킷: 경계에서 몰리는 요청을 막는다. 대신 구현과 테스트가 복잡하다.
- IP 판단
  - `getRemoteAddr`만 사용: 클라이언트가 바꿀 수 없다. 대신 프록시 뒤에서는 모든 요청이 프록시 IP로 보인다.
  - `X-Forwarded-For` 사용: 프록시 뒤에서도 실제 클라이언트를 구분한다. 대신 신뢰할 프록시를 정하지 않으면 클라이언트가 헤더를 위조해 제한을 우회한다.

## 결정
- 서버 메모리에 센다. 서버 한 대짜리 개인 프로젝트라 외부 저장소(Redis 등)는 운영 부담만 늘린다.
- 고정 창을 쓴다. 구현과 시계 주입 테스트가 단순하다.
- IP는 `getRemoteAddr`만 쓴다. `X-Forwarded-For`는 클라이언트가 위조할 수 있어 믿으면 제한을 우회당한다.
- 구현: `IpRateLimiter`(창이 바뀌면 지난 창 항목 삭제, 카운터 창은 뒤로 가지 않음), 미리보기는 `/api/preview` POST 인터셉터. 시계는 `ClockConfig` 빈.

## 결과
- 얻는 것: 추가 구성 요소 없이 제한을 둔다. 창 경계와 초기화를 고정 시계로 테스트할 수 있다.
- 감수하는 것
  - 재시작하면 카운트가 초기화된다.
  - 창 경계에서 최대 2배까지 통과한다. 미리보기는 LLM 비용이 없고, 작업 생성은 F2의 Claude 하루 호출 상한이 따로 막는다.
  - IPv6는 주소마다 따로 세므로 같은 대역에서 주소를 바꿔 가며 보내면 우회된다. 한 창 안에서 추적하는 IP 수에도 상한이 없어, 그런 요청이 계속 오면 그 창 동안 메모리가 늘어난다 (다음 창에서 지워짐).
  - 프록시 뒤에 배포할 때는 신뢰 프록시 설정으로 다시 결정한다. IPv6는 주소 대신 /64 대역 단위로 세는 방식을 그때 검토한다 (docs/plans/F1-script-input.md 배포 시 점검).
