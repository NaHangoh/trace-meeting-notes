# 0007. 정리는 메모리 대기열과 작업자 하나로 비동기 처리
- 날짜: 2026-10-08
- 상태: 확정

## 배경
정리(F2)는 로컬 LLM 호출이라 한 번에 수 분이 걸릴 수 있다(호출당 타임아웃 5분). 요청 스레드에서 LLM 응답을 기다리지 않는다(rules/backend.md). 개발 노트북은 내장 GPU와 공유 메모리(평소 여유 약 10GB)로 7~9B급 모델 하나를 돌린다. 서버는 한 대다(ADR 0006).

## 선택지
- 전역 1개 + 대기열 상한: 실행기 하나가 한 번에 하나씩 처리하고 나머지는 '대기'로 줄을 선다. 대기열이 차면 거부한다.
- 전역 2개: 실행기가 병렬 요청을 받게 한다. 내장 GPU와 공유 메모리에서는 작업마다 느려지고 메모리가 부족할 수 있다.
- 전역 1개 + IP당 1개: 한 사람이 대기열을 채우는 것을 막지만 개발 중에는 불편하다.

## 결정
- 정리 작업은 전역 1개만 실행한다. 대기열은 서버 메모리에 두고 최대 10개(설정값)다.
- 대기열이 차면 작업 생성과 다시 시도를 429 `QUEUE_FULL`로 거부하고 작업을 만들지 않는다. 요청 수 제한(`TOO_MANY_REQUESTS`)과 오류 코드·화면 문구를 구분한다. 기존 `TOO_MANY_REQUESTS` 이름은 그대로 둔다.
- 서버가 시작될 때 `QUEUED`·`RUNNING`이던 작업은 `FAILED`(`SERVER_RESTART`)로 바꾸고, 사용자가 다시 시도할 수 있다.
- IP당 동시 1개 제한은 공개 배포 시 추가한다 (SPEC S4).
- 이 방식을 고른 이유: 내장 GPU와 공유 메모리(평소 여유 약 10GB)에서 정리를 병렬로 돌리면 둘 다 느려지고 메모리가 부족할 위험이 있다. 혼자 쓰는 로컬 실행이라 한 번에 하나씩 처리해도 충분하다.

## 확장 경로
- 작업자 수는 설정값 `app.summary.workers`(기본 1)다. llama-server를 `--parallel N`으로 띄우거나 외부 API를 쓰게 되면 늘린다.
- 대기열은 `SummaryQueue` 인터페이스 뒤에 두고 지금은 메모리 구현을 쓴다. 서버를 여러 대로 늘릴 때는 DB 구현(작업 테이블에서 `SELECT … FOR UPDATE SKIP LOCKED`로 대기 작업을 가져옴)으로 바꾼다.
- 요청 수 제한기(ADR 0006)도 서버 메모리에 있으므로, 여러 대로 늘릴 때는 Redis나 DB로 옮겨야 한다.

## 결과
- 얻는 것: 추가 구성 요소(메시지 큐, 외부 저장소) 없이 비동기 처리, 실행기 하나에 맞는 부하
- 감수하는 것
  - 서버를 다시 시작하면 대기·진행 중이던 작업은 실패가 되고 사용자가 다시 시도해야 한다.
  - 대기열 10개를 다른 사용자들이 채우면 새 작업을 만들 수 없다 (IP당 제한은 공개 배포 시).
  - 서버가 여러 대면 대기열을 나눠 갖게 되므로 다시 결정해야 한다.
