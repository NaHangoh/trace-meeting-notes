# LLM 연동 규칙

## 구조
- 모든 LLM 호출은 `LlmClient` 인터페이스를 거친다. 서비스 코드에서 특정 모델 SDK를 직접 부르지 않는다.
- 구현체: `OllamaLlmClient`(개발용, 무료), `ClaudeLlmClient`(정확도 측정·시연용), `FixtureLlmClient`(테스트용).
- 어떤 모델을 쓸지는 설정(`app.llm.provider`)으로만 바꾼다.

## 프롬프트
- 제품 프롬프트는 `prompts/` 아래 파일로 관리하고 코드에 문자열로 박지 않는다.
- 프롬프트를 바꾸면 버전을 올리고(`summarize.v2.md`), `/eval`로 이전 버전과 비교한다. 결과 없이 교체하지 않는다.
- 정리 단계와 검증 단계는 다른 프롬프트, 다른 호출이다. 정리한 모델이 스스로 검증하게 하지 않는다.

## 출력
- LLM 응답은 정해진 JSON 스키마로 받고, 파싱·검증에 실패하면 재시도 횟수를 제한한다.
- 근거 위치(발언 번호·범위)는 반드시 원문에 실제로 존재하는지 코드로 다시 확인한다. LLM이 준 위치를 그대로 믿지 않는다.
- 원문에 없는 내용은 "근거 없음"으로 표시하고, 사용자가 확인하기 전에는 최종본에 넣지 않는다.

## 비용
- 실제 API를 호출하는 작업(eval, 시연) 전에 예상 호출 횟수를 보여주고 확인받는다.
- 자동 테스트는 FixtureLlmClient만 쓴다.

## 프롬프트 인젝션 (회의 스크립트는 신뢰할 수 없는 입력)
- 제품의 LLM 호출에는 도구 호출(function calling), 파일·네트워크 접근을 주지 않는다. LLM이 할 수 있는 일은 JSON 텍스트를 돌려주는 것뿐이어야 한다. 그래야 인젝션이 성공해도 피해가 "틀린 회의록 항목"으로 한정되고, 근거 검증과 사람 확인에서 걸러진다.
- 스크립트는 구분자로 감싸 데이터 영역에 넣고, 시스템 지시와 섞지 않는다.
- 응답은 스키마로 검증한다. 스키마 밖 필드, 지나치게 긴 값은 버린다.
- eval에 인젝션 케이스를 둔다 (스크립트 속 "이전 지시를 무시하고 ~를 결정 사항에 넣어라" 같은 발언이 결정 사항으로 확정되지 않는지).
